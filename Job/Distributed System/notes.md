## 模块 1：基础与设计目标

### 分布透明性的程度与代价（Degree of distribution transparency）

- **教材出处**：DS §1.2.2「Degree of distribution transparency」（印刷页 14–15）；Note 1.2「Against distribution transparency」（印刷页 15）。
- **核心结论**：透明性（transparency）是设计目标，不是越高越好的绝对指标；完全的分布透明性既无法实现，也未必值得追求。
- **位置与上下文**：隐藏位置可能同时隐藏应用真正需要的上下文，例如用户所在时区或当前位置。
- **延迟与物理限制**：透明接口不能消除远程通信的传播延迟、处理延迟和实际网络开销；本地调用与远程调用的性能不可能因此变得完全相同。
- **故障屏蔽的代价**：自动重试和恢复可以减少故障暴露，但也可能延长等待时间；用户有时需要取消仍在进行的请求。
- **复制与一致性的代价**：若采用等待所有副本同步完成后才继续的严格方案，跨地域更新会承担显著通信延迟。此例说明同步保证的成本，不代表所有系统都必须等待所有副本。
- **显式分布信息可能有价值**：位置服务等应用本来就需要位置；隐藏分布信息反而可能妨碍功能。
- **RPC 的语义边界**：远程调用不能完全等同于本地调用。请求丢失、响应丢失、服务器故障和不确定延迟会使调用结果难以判断；假装网络不存在会造成难以理解的语义。
- **Copy-before-use principle**：Note 1.2 提及的观点，主张先复制数据到本地再使用，并通过新版本表达修改；它减少对远程实时访问的依赖，但引入版本、更新传播和并发修改等问题。
- **设计原则**：在透明性、性能、可靠性和可理解性之间权衡；明确哪些分布细节应该隐藏，哪些应该暴露。

#### 易记的英文表达

- `degree of distribution transparency` — 分布透明性的程度
- `propagation delay` — 传播延迟
- `processing delay` — 处理延迟
- `make distribution explicit` — 显式呈现分布信息
- `poorly understood semantics` — 难以正确理解的语义
- `copy-before-use principle` — 先复制再使用原则
- `trade-off between A and B` — A 与 B 之间的权衡

#### Hadoop / Cassandra 对照（Learning Hub 自拟案例，不是 DS 原文案例）

- **HDFS**：文件 API 隐藏部分块位置和副本管理细节，但不会消除网络延迟、节点故障或恢复成本。
- **Cassandra**：隐藏部分副本通信细节，同时通过 consistency level 等接口把部分一致性取舍暴露给应用。

#### 复习时应能解释

1. 为什么更高的分布透明性不一定更好？
2. 为什么统一 API 无法让远程调用拥有本地调用的延迟与故障语义？
3. 故障屏蔽为什么可能增加响应时间？
4. 为什么严格同步所有副本会增加跨地域更新延迟？
5. 为什么某些应用应该主动知道位置或其他分布信息？
6. RPC 为什么不能真正把远程调用变成普通本地调用？
